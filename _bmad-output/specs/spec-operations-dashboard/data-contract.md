# Dashboard data and interaction contract

This is a logical read contract, not a migration or an assertion that these fields already exist. The approved task-ownership decision in SPEC.md supersedes independent booking-unit classification: current reconciled bike tasks define dashboard bike scope. Detailed product catalogue and scenarios remain in the adopted product document.

## Period and query boundary

The server resolves the selected period from URL parameters against one captured Madrid business date. Calendar membership uses inclusive local start date and exclusive day after the local end date; do not add fixed 24-hour UTC durations across DST. Today, Tomorrow and Next 7 Days match existing Workshop logic (today through today+6). Next Week is the next Monday through Sunday; Next Month is the next complete calendar month (approved Q2), both resolved in Europe/Madrid. A custom range includes both named dates. Parameter names and invalid-range UX remain implementation details to document and test; never execute an unbounded accidental query on malformed input.

Resolve order inclusion once, then independently select starts and stops within the range. Include only reserved, started and stopped orders. Exclude new, draft, canceled and archived orders from rows and every summary/day total even if Workshop tasks remain or dates are in range; preserve those tasks and their history unchanged. Membership uses scheduled start/return timestamps independently of lifecycle progress. A missing Booqable order number does not exclude an otherwise eligible order; show “Booqable order number missing”. Start from orders so zero-task orders survive; join per-order aggregates computed separately before combining lines, assignments, tasks and events to prevent join multiplication. Canonical current-task scope is AD-1: rental_turnaround tasks on open assignment instances (`closed_at IS NULL`), excluding cancelled tasks and including completed tasks while the assignment remains open. Use it for every bike count, status breakdown and current-task link; history is preserved but excluded from this operational list. A task’s cached `starts_at` can differ from order data after terminal state; scheduled membership uses order timestamps.

Existing `bookings_view` and `workshop_tasks_view` are useful evidence but neither supplies the required contract. Adopt one staff-authorized PostgreSQL read function for the selected Madrid range, returning order rows, task breakdowns, day groups and totals from one coherent dataset under authenticated user/RLS access. Do not inherit the bookings view’s missing-number exclusion. Keep source sync, external routing and selected-order detail outside this read function; SQL object names/internal stages are implementation details. No large arrays aggregated in Node/browser and no per-row detail RPCs. Use the existing user Supabase client. Do not implement a new reconciliation pipeline.

## Logical fields

| Record | Required fields / semantics |
|---|---|
| Period | Mode, local start/end dates, Europe/Madrid, captured reference time; enough URL state to restore the view. |
| Dashboard result | Period, aggregate summary, day groups, outgoing/incoming orders, sync evidence, explicit `error`; optional ETA failures are separate from workload failure. |
| Summary/day | Outgoing orders/bikes, incoming orders/bikes, outgoing delivery orders, preparation workload, missing-address delivery orders. Preparation workload counts current tasks in to_prepare, being_prepared or needs_recheck for eligible outgoing orders in the selected period (approved Q8); no rolling 24-hour filter. Bike counts describe current reconciled task scope, not an independent count of booked units. |
| Order identity | Local UUID for drawer, Booqable ID for existing integration, nullable Booqable order number and display customer name; no invented customer/rider identity. Show “Booqable order number missing” when absent and keep drawer navigation via local UUID. Booqable order number, Booqable integration ID and local UUID are distinct. Keep missing-name presentation explicit. |
| Schedule/state | Start/stop instant, Madrid day/time, raw order status, pickup/delivery/unknown fulfillment, relevant source evidence; incoming collection context only when reliably available. |
| Bike scope | Current reconciled bike-task count is the canonical denominator and bike count. Preserve partner units and distinguish current tasks from retained history. Do not classify source order lines again or compare booked quantities to detect missing/extra tasks. |
| Readiness | Counts by exact task status; ready count, preparation-stage outstanding count, lifecycle counts, configuration/source-change notices, authorized task IDs for navigation. Preserve one task per unit, including synthetic partner units. |
| Delivery | Use delivery_address first; if empty, use maps_link_order. Record the selected field and preserve address versus location-link form. Both empty means missing. Approximate duration uses the adopted Google boundary; inability to resolve or route the supplied value does not make it missing. |
| Warning | Stable condition kind, affected order/task identity, affected count when known, severity, plain text, evidence and authorized resolution target. No mutation instruction in the read model. |
| Sync | Run ID, scope, state, cursor, listed/succeeded/failed/skipped, last attempt/error, linked successful-run evidence where available; coverage limitations travel with the label. |

## Status mapping grounded in Workshop

| `bike_tasks.status` | Dashboard meaning |
|---|---|
| `to_prepare` | Preparation outstanding. |
| `being_prepared` | Preparation in progress; outstanding. |
| `needs_recheck` | Recheck outstanding; normal M1→M2 stage or existing recheck evidence, not automatically an allocation-change diagnosis. |
| `ready_for_pickup` | Ready numerator, only for current eligible bike task scope. |
| `in_rental` | Already handed over; lifecycle state, not preparation outstanding. |
| `returned` | Returned; turnaround/storage remains, not outgoing preparation failure. |
| `prepare_for_storage` | Storage work in progress; lifecycle/turnaround context. |
| `completed` | Completed lifecycle, not an unprepared bike. |
| `cancelled` | Not current ready work; preserve cancellation/history diagnostics. |

Echelon owns task creation; Operations trusts the current reconciled bike tasks. Eight current tasks with six ready yield 6/8 ready. Seven current tasks, all ready, may yield 7/7 regardless of source booking quantity; auditing reconciliation completeness is outside this dashboard. Do not calculate preparation outstanding as total minus ready when tasks are in-rental/returned/completed: that would turn lifecycle progress into alarms. An otherwise eligible order with zero current bike tasks stays visible and is highlighted as an exceptional condition; do not label it all ready or infer a reconciliation failure. Use one consistent “No Workshop tasks” highlight across all periods and directions, with no urgency notification or time-based escalation. Zero-task absence does not enter preparation-urgency calculations. For mixed lifecycle states, show the status breakdown instead of a bare ready/total ratio (approved Q6): for example, 3 ready, 3 in rental, 2 to prepare. Only preparation-stage tasks count as preparation outstanding. The owner provided partial returns as context only; no new return workflow is in scope. Do not count checklist items or add-on records as bike tasks or introduce a dashboard-specific product classifier.

## Warnings and page composition

Use header/timeframe/sync controls, workload summary, concise attention, Going out, Coming back in that order. Today/Tomorrow are chronological; multi-day views group by local day. Outgoing rows show time, customer/reference, fulfillment, bikes/readiness, actual delivery address, approximate drive time, concise warnings and useful relative start time on Today. Incoming rows show return time, customer/reference, bikes and reliable collection context; automated tight-turnaround detection is deferred beyond V1. Price/payment detail stays in the drawer.

Missing address is visible for all periods, prominent Tomorrow and high priority Today. Today preparation-outstanding urgency uses named configuration values: more than 6 hours until start is low emphasis; more than 2 hours through exactly 6 hours is warning; exactly 2 hours or less, including overdue, is critical (approved Q1, revisable later). Apply to preparation-stage tasks only. Apply these thresholds to outgoing rows whose scheduled start is on today’s Europe/Madrid date in every selected range, including Next 7 Days and custom ranges (approved Q9). Other dates receive no readiness urgency. Keep configuration/scope/source inconsistencies visible; do not label future unprepared bikes urgent. Allocation/add-on recheck warnings require existing evidence beyond merely `needs_recheck`. Automated tight-turnaround detection is outside V1 (approved Q7). Current per-order status breakdown remains visible, including returned/awaiting storage preparation and prepare_for_storage/storage work in progress; these are distinct states, neither outstanding outgoing preparation.

Deduplicate the same condition for an order/task; summary counts may reference row warnings without another large repeated card. Keep chronological context even if critical attention is promoted. Warning precedence for simultaneous conditions must be documented alongside approved thresholds, without suppressing a distinct issue. An empty section states no outgoing/incoming orders; failed/unknown coverage remains separately visible. Exact component names/layout styling are not frozen by this spec.

Mount the existing drawer host under the staff Operations layout and reuse its query-parameter hook/close behavior. Approved Q13: extend the shared drawer with staff-authorized current bike-task links to /workshop/[taskId]; historical tasks stay outside this operational list. Fetch the selected order’s task links on demand with existing user/RLS boundaries; never expose Workshop data to partners merely because they can open an order. Retain existing task routes and errors. Preserve keyboard activation, focus return and non-color status text. Do not add detail fetches for every dashboard row.

## Honest sync confidence

**Approved target (supersedes reserved-only reuse scope below):** Dashboard refresh covers its selected Madrid period, including Next Month, for outgoing or incoming reserved/started/stopped orders. Reuse reconciliation and run infrastructure, extending discovery, fixed date-window metadata and resume semantics; report progress/failures without blocking local workload rendering. Include refresh of locally eligible candidates so source cancellation/date changes can remove stale rows. Exact implementation and optimization are not present yet. Separate research task on feature/optimize-sync-with-booqable investigates existing slowness; no batch/concurrency redesign is adopted by this document. The following describes current evidence and reusable behavior, not proof of implemented selected-period coverage.

`startManualSync("next_7_days")` and `resumeManualSync(cursor)` already wrap authenticated actions. The owner explicitly approved this narrow service-role worker exception (Q12); Dashboard and drawer reads stay user/RLS-bound. The start RPC checks staff role before the privileged worker; manual and per-order leases, cursors and retry result counters stay intact. The next-seven-days start walks reserved-list pages; resume continues the encoded page. Results count skipped rows separately from successful reconciliations. Reuse queue progress/final-result patterns, realtime coalescing and stale-in-progress detection; a pending run is not success.

| Evidence | Permissible meaning / label |
|---|---|
| No health/read failure | “Sync confidence unavailable” or explicit load error, never a fresh complete empty workload. |
| `in_progress` and live evidence | “Checking upcoming reserved orders…” plus existing progress. Cursor/stale run state must remain distinguishable and recoverable. |
| Failed run or unfinished cursor | “Upcoming-order sync failed/incomplete” plus existing outcome and recovery action; list may be incomplete. |
| Successful run whose scope and completion time are linked | “Reserved orders starting in the next 7 days checked at …” (or “All reserved orders checked at …” for that scope). This proves only that run’s candidate scope at that time. |
| `workshop_sync_health.last_success_at` alone | Last successful manual sync time only. The view attaches the latest run independently, so do not borrow its scope to describe an older success. |
| One order/webhook processed | Per-order evidence only; never dashboard-global freshness. Current health view does not supply durable failed-webhook coverage. |

If scoped successful history is required, query the matching `booqable_sync_runs` record rather than pairing unrelated view columns. Existing rows do not store an explicit covered date interval; a run crossing midnight/resumed later may use changing current-day filters. Do not reconstruct a guaranteed coverage interval merely from its finish time. The action is not a promise to refresh incoming started orders, missed historical webhook deliveries or Next Month. This is the existing reserved-only scope. Approved AD-10 extends recovery to the selected outgoing/incoming period without adding a scheduled poller. New run labels must use their recorded interval, for example “Orders starting or returning 1–31 October checked at …”; only complete enumeration and successful required reconciliations permit that label. Retain old labels only for old scope evidence.

## Delivery ETA boundary

Google Routes API v2 Compute Routes is approved, with DRIVE and TRAFFIC_UNAWARE. The owner delegated remaining routing engineering choices. Reuse `BUSINESS_ADDRESS = Carrer del Cardenal Rossell 35, Palma` as the shop origin seed, verifying the precise destination before rollout; no new origin-entry UI. A Maps embed is not driving-duration infrastructure. Existing parser/SQL persist both delivery_address and maps_link_order. Approved Q3 precedence is delivery_address then maps_link_order; shared fallback/display integration must be added when implementation is authorized. Do not use billing_address. Resolve only supported/tested Maps-link destination forms; arbitrary share URLs are not Routes API waypoints. Do not treat viewport coordinates as destination coordinates or scrape Maps page content. Unsupported or ambiguous links retain the original delivery link with drive time unavailable; short-link expansion, if implemented, must restrict every redirect to allowed Google Maps hosts and bounded requests.

The accepted boundary is a staff-authorized server request using only required origin/destination data, never customer name/phone or browser secrets. Keep the displayed source value unchanged. No persistent route-duration cache or cross-request response cache in V1; this supersedes the provisional cache/TTL requirement. Deduplicate identical origin/destination/mode requests within the current load and avoid polling or refetching on drawer open/close. Load estimates separately from workload, with bounded concurrency/timeouts and no automatic retry loop. Require a server-only restricted key, usage quotas and Google Maps attribution; exact operational settings are implementation configuration to verify before rollout. Ten thousand is a monthly free allowance, not an automatic hard cap. Ambiguous addresses must not silently choose a destination. Missing address, unavailable route and aggregation failure remain distinct. Routing timeout/quota/outage must not delay or erase core workload; log sanitized condition/provider outcome without full addresses or credentials. No live traffic, driver origins or multi-stop routing.
